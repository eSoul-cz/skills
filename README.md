# eSoul Skills

Reusable agent skills and companion tools for eSoul projects, installed in layers.

**Version.** The Claude Code plugin (`esoul-skills`) is at **0.27.1**; each release is tagged `plugin-<version>` (the bare `0.6.x` tags belong to the documentation tool). The helper package `@esoul-cz/skills` has its own version in `package.json` (0.2.1 ships with plugin 0.27.1). Maintainers are listed in [`CONTEXT.md`](CONTEXT.md).

**Principles.** The guidelines (`eSoul-cz/guidelines`) are the source of truth; a skill holds only the procedure for an agent and points to the guideline by file and heading. The eSoul skills build on [mattpocock's skills](https://github.com/mattpocock/skills), which are installed from their source and never copied here. Every layer works without the optional ones; a skill that uses a more optional skill says what to do when it is missing. Agents, hooks and Codex files are optional.

## Layers and skills

Each developer picks layers, and skills inside a layer. Layers marked *project* go into every project; layers marked *user* are installed for the person. The skills of the third-party layers are never copied here: they are installed from their own repositories. [`layers.json`](layers.json) is the single definition (scope, requires, own skills, third-party sources); the skills live in `skills/<layer>/<skill>/`, and each `SKILL.md` holds its own usage. The list below is generated (`node tooling/scripts/build_readme_skills.mjs`; the `Verify skills` check fails when it is stale).

## Install

The helper is a Node package on top of [`npx skills`](https://github.com/vercel-labs/skills). Its one runtime dependency is `@clack/prompts`, loaded only for the interactive selector, so `--yes`, `--dry-run` and script runs never load it:

```bash
# in a project: core, dev and upstream-core, plus the stack skills that match the project
# (LSR, Vue/Inertia; Laravel is checked for Boost) and esoul-jenkins-libraries when the project
# has a Jenkinsfile and you can read that private repository; commit skills-lock.json and
# .agents/skills/ afterwards
npx @esoul-cz/skills project init                 # --stack lsr,vue to choose, --no-stack to skip them; in a terminal it opens the selector (below)

# layers, with the layers they require; project layers go into the project, user layers are global
npx @esoul-cz/skills install dev
npx @esoul-cz/skills install project helpers business
npx @esoul-cz/skills install upstream-picks:wordpress,web
npx @esoul-cz/skills install upstream-picks:matt-extra       # the rest of mattpocock's set (off by default)
npx @esoul-cz/skills install helpers --optional                # also the test queue
npx @esoul-cz/skills install dev --skill esoul-review,esoul-testing   # chosen skills of the layers
npx @esoul-cz/skills install                                   # in a terminal: the selector, target then layers then skills

npx @esoul-cz/skills layers      # what the layers contain
npx @esoul-cz/skills status      # which layers and skills are installed, project and user; flags retired names and stale lock entries
npx @esoul-cz/skills retired     # the retired skill names, what replaced them, and the git grep that finds them in project files
npx @esoul-cz/skills agents claude|codex   # optional worker agents and hooks
```

Useful options: `--dry-run` prints the `npx skills add` commands, `--yes` adds required layers without asking, `--agent <name>` and `--copy` go to `npx skills`, `--target auto|project|user` (aliases `--project`/`-p` and `--global`/`-g`) says where the layers go: `auto` (the default) puts every layer where `layers.json` says, project layers into the project and user layers for the person, `project` or `user` put all of them there. The helper refuses to install a layer whose required layers are missing and offers to add them. `--help` (or `-h`) of any command prints the usage and installs nothing.

**Interactive selector.** `install` with no layer and `project init`, in a terminal and without `--yes` (or a layer or `--skill` argument), ask in three steps instead of installing at once: the target (`auto`, `project` or `user`; preselected from the command: `project init` and `--project`/`-p` → `project`, `--global`/`-g` → `user`, otherwise `auto`), the layers (core, dev and upstream-core preselected, plus the stack groups `project init` detected; each is shown with where it goes, for example `core (project)`; the layers a chosen layer requires are added after a question), and the skills of those layers grouped by layer, third-party sources included, all selected (deselect one to skip it). `--dry-run` prints the commands and installs nothing. Without a terminal, with `--yes` or with layer or `--skill` arguments nothing is asked and the helper behaves as a script expects.

The skills are installed with one `npx skills add` per source repository and scope (`auto` can give a project and a user command for the same repository): a full `install` of every layer takes 10 commands instead of 15, `project init` 4 instead of 5. Whenever a project-scope command ran, the helper reminds you to commit `skills-lock.json` and `.agents/skills/`.

**New developer.** A project commits `skills-lock.json` and `.agents/skills/`, so after the clone its skills are already there:

```bash
git lfs pull                                   # where the project keeps assets/ or .pen files in LFS
npx skills experimental_install                # only to restore or refresh the project's skills from the lock
npx @esoul-cz/skills install project helpers   # optional, once per person: your own layers (user scope)
```

The user layers are not part of the project; `status` shows what is installed. Update with `npx skills update -p` (project) and `npx skills update -g` (user).

**Compatibility.** Several skills cite guideline sections that exist only from `esoul-cz/guidelines` 0.5.0 (`workflow.md` › Hotfix and the standing small-admin record, project exceptions). On an older project, raise the constraint (`composer require --dev esoul-cz/guidelines:^0.5 -W`, [`setup.md`](skills/project/esoul-project-update/references/setup.md)); until then `esoul-guidelines` offers the update when a cited heading is missing.

**Updating a project's skills (also from before 0.26.0).** `project init` does the whole update of the project scope: it installs the current set (and rewrites a moved lock path), then removes the retired skills (the `retired` map of [`layers.json`](layers.json); `retired` prints it) and the lock entries whose skill their source no longer lists (an upstream source such as `mattpocock/skills` dropped or renamed it; found with `npx skills add <source> --list`) in one `npx skills remove … -y`, and refreshes the rest from the lock with `npx skills update -p -y`. A skill the project took from a source outside `layers.json` stays. The removal asks first in a terminal (default yes), runs with `--yes`, and without a terminal or `--yes` only reports it and says to pass `--yes`; `--dry-run` prints the commands. Global skills are never touched there: `status` reports retired and stale ones of both scopes and prints the commands. Review the diff afterwards (`.agents/skills/`, `skills-lock.json`); the project's own files may still name a retired skill (`retired` prints the names and the `git grep`). The whole procedure with the guidelines version is the setup update of `esoul-project-update` ([`references/setup.md`](skills/project/esoul-project-update/references/setup.md)).

Without the helper, the raw `npx skills` commands work too:

```bash
npx skills add eSoul-cz/skills --list
npx skills add eSoul-cz/skills --skill esoul-workflow esoul-guidelines esoul-task-work
npx skills add mattpocock/skills@v1.3.2 --skill code-review tdd diagnosing-bugs grilling handoff prototype codebase-design domain-modeling
npx skills add freeloio/freelo-cli --skill freelo
```

Start any real task with the entry point:

```text
$esoul-workflow build, fix, review or analyse this eSoul task
```

## Optional: agents, hooks and Codex

No skill needs them. They are a convenience for people who use Claude Code or Codex with orchestrated subagents.

- **Agents and hooks.** `agents/` holds seven worker agents with pinned models (`scout`, `test-runner`, `implementer`, `reviewer`, `critical-reviewer`, `uat-runner`, `ops`). `scout`, `reviewer` and `critical-reviewer` are read-only by their rules; `ops` may use only shell, read and search tools, the `Skill` tool and the Freelo MCP server (`mcp__freelo__*`, so the server must be named `freelo`; Claude Code enforces the list); `uat-runner` needs a browser tool that can use a dedicated profile, in Claude Code and in Codex alike. `hooks/` injects the usage rules at every session start (explicit model, never a fork, size S directly, take over after two failed attempts, and the session-title line) and denies Explore, forks and general-purpose agents without an explicit `model` (disable with `ESOUL_AGENT_GUARD=off`; needs Node 22+). Skills describe delegation by job, never by agent name. The role briefs are in `skills/helpers/esoul-model-routing/references/roles.md`, generated from `agents/*.md` (`node tooling/scripts/build_roles.mjs`), so an agent without the plugin can brief any subagent with the same rules.
- **Claude Code plugin** (agents, hooks and the skills as one plugin):

  ```bash
  claude plugin marketplace add eSoul-cz/skills
  claude plugin install esoul-skills@esoul          # eSoul skills (all layers) with agents and hooks
  claude plugin install mattpocock-skills@esoul     # optional: the full upstream set
  claude plugin install frontend-design@esoul       # optional: distinctive, non-templated UI
  ```

  The plugin reads the layer folders (`skills` in `.claude-plugin/plugin.json`). **0.26.0 is a breaking change:** the skills were renamed and moved between layers (`esoul-tasking` → `esoul-task-work` and `esoul-task-create`, `esoul-freelo-task-authoring` → `esoul-task-create`, `esoul-maintain-application-documentation` → `esoul-docs`, `esoul-project-data` and `esoul-data-task-guard` → `esoul-data`; new `esoul-guidelines` and `esoul-testing`); the `freelo` copy, `test-queue` and the `esoul-awesome-picks` plugin are gone (install `upstream-core`, [`eSoul-cz/test-queue`](https://github.com/eSoul-cz/test-queue) and `upstream-picks` with the helper). Install the third-party skills with `npx @esoul-cz/skills install upstream-core`.
- **Codex** (agents to `~/.codex/agents`, rules into `~/.codex/AGENTS.md`):

  ```bash
  git clone https://github.com/eSoul-cz/skills && cd skills
  node codex/install.mjs            # --dry-run shows what would change; merge codex/config.toml by hand
  ```

  Or `npx @esoul-cz/skills agents codex`. A Codex custom agent file cannot set the sandbox, approvals or MCP servers (they come from the parent session), so in Codex the read-only agents only lose their connectors (`features.apps = false`) and `ops` has no tool list; run review sessions in a read-only sandbox if that matters. After editing `agents/`, regenerate the Codex agents, `codex/AGENTS.md` and `hooks/session-rules.md` with `node tooling/scripts/build_codex_agents.mjs`, and the role briefs with `node tooling/scripts/build_roles.mjs`; the checks fail when they are stale.

Usage report (where the weekly limit goes): `node tooling/scripts/usage-report.mjs --days 7`.

## Upstream skills the eSoul workflow does not use by default

The tracker and setup skills of mattpocock's set, `pr` and `git-guardrails-claude-code` replace an eSoul rule or tool, so they are the on-request group `upstream-picks:matt-extra`. `esoul-workflow` › `references/upstream.md` is the one place that says what eSoul adds to each upstream skill and when an agent leaves one alone.

## Publishing the helper

`@esoul-cz/skills` is published on npm by the `esoul-cz` organisation (first release 0.1.0, 2026-11-24): `npx @esoul-cz/skills <command>`.

A release is published by hand, because it is rare and needs no build: bump `version` in `package.json` (semver: a new layer or command is minor, a breaking command change is major), commit, then `npm publish --access public` from the repository root (`publishConfig.access` is already `public`). Jenkins does not publish to npm and needs no npm token.

From a checkout without npm access, run `node bin/esoul-skills.mjs <command>`.

## Checks

```bash
tooling/scripts/test_skills                    # every Node test (needs git and the network for the source check)
tooling/scripts/test_python                    # the Python tests of the skills (python3, or the python:3 image)
node tooling/scripts/build_readme_skills.mjs   # regenerate the layer list above; --check only verifies it
node tooling/scripts/check_upstream.mjs        # newer releases of the pinned third-party sources (exit 1 on drift)
ESOUL_SKIP_NETWORK=1 node --test tooling/scripts/test_skills.mjs tooling/scripts/test_layers.mjs tooling/scripts/test_layers_manifest.mjs
```

They cover: skill frontmatter and description budget, relative links, one layer per own skill and a valid `layers.json`, every source of `layers.json` resolving (`npx skills add <source> --list`, the pinned mattpocock tag included), the generated README list, Codex agents, hook rules and `roles.md` in sync, no skill naming the optional agents, the script tests of the skills, the review script tests and anonymised review eval cases, the gitmoji catalog and the usage report. Jenkins runs each group only when its files changed, everything on a schedule and on a tag (`Jenkinsfile`); a weekly scheduled build also reports pinned upstream sources with a newer release (build turns unstable). The mockup preview test (`tooling/scripts/test_mockup_preview.mjs`) needs an application checkout and Chrome and stays manual.

## Tools

- `docs/documentation` validates and renders application documentation (the optional PDF part of `esoul-docs`). Install it in an application repository with:

  ```bash
  curl -fsSL https://github.com/eSoul-cz/skills/releases/latest/download/install.sh | sh
  ```

- `freelo` is the authenticated CLI behind the official Freelo skill (layer `upstream-core`). Authenticate it with `freelo auth login`.

Tooling source and release automation live under `tooling/`, `install.sh`, and `Jenkinsfile`.
