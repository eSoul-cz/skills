# Two-axis review: the eSoul additions

The flow of `esoul-review` Path A is the installed `code-review` skill (layer upstream-core): take a fixed point, identify the spec and standards sources, review on two axes with parallel fresh-context reviewers, aggregate without reranking. Use it as written. When it is not installed, ask the user to run `npx @esoul-cz/skills install upstream-core`, or follow the additions below alone: a **Standards** axis (does the diff conform to the documented standards) and a **Spec** axis (does it implement the issue or task, acceptance criteria and `## UAT` included), each reviewed by a reviewer with a fresh context (a subagent when the harness offers them, otherwise a clean pass of your own), reported under `## Standards` and `## Spec`, never merged or reranked across the axes.

What eSoul adds to it:

1. **Fixed point.** `esoul-review` step A1 already produced the diff: use its `diffCommand` (three-dot against the merge base, plus staged, unstaged and untracked changes for the default scope) and `git log <base>..HEAD --oneline`. A bad ref or an empty diff stops the review before any reviewer starts.
2. **Spec source**, in this order: the issue or task linked from the branch name, PR body or commit messages (`#123`, `Closes #45`, a Freelo task id), fetched with `gh` or the `freelo` skill, with its acceptance criteria and `## UAT`; a path or link the user passed; a plan slice or spec under `docs/` that matches the branch name (a project on `profile/internal` works from a plan slice or the owner's request); otherwise ask where the spec is. With none, skip the Spec axis and say "no spec available".
3. **Standards sources:** `AGENTS.md`, `CONTEXT.md`, `docs/project_guidelines/code-review.md` and `workflow.md` always, the other guideline files when the touched area matches, `accepted` ADRs of the touched areas, `GLOSSARY.md`, `CODING_STANDARDS.md` when present. The checklist order is `code-review.md` › What a reviewer checks against. A documented project standard always wins over upstream's smell baseline, which is a judgement call at Minor at most.
4. **Reviewer briefs.** Both axes get the header in [review-passes.md](review-passes.md#briefs) (scope, rules, findings already decided). The Standards brief adds the project's default Critical findings, the [tests lens](review-passes.md#tests-lens) and the [stack notes](review-passes.md#stack-notes) of the touched stacks; the Spec brief adds the [defect probes](review-passes.md#defect-probes), which sharpen "looks wrong". The reviewer's strength follows [Choosing the reviewer](review-passes.md#choosing-the-reviewer).
5. **Severity names** are the guidelines' (`docs/project_guidelines/code-review.md` › Severity); each axis's findings are verified, deduplicated and classified after aggregation (`esoul-review` step A5).
6. **Findings stay in the PR:** the conversation, the work ledger and PR threads, never a repository file (`code-review.md` › Findings stay in the pull request). When CodeRabbit is limited, the findings go into the PR as a fallback review (step A9, [pr-comments.md](pr-comments.md)).
