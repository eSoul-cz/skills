# Project guidelines - Frontend

These guidelines define the standard for frontend code. Code that contradicts them is a bug to
fix, not a precedent to follow.

The stack is Inertia, {{FRONTEND_FRAMEWORK}}, TypeScript, Laravel Wayfinder, Tailwind CSS 4,
shadcn ({{SHADCN_VARIANT}}) and Vitest. `package.json` and its lockfile are authoritative for
versions. Domain behaviour, validation and authorization stay on the server; the frontend owns
presentation, interaction state and client-side orchestration only.

## Project structure and locality

```text
resources/js/
├── pages/            # Inertia page entry points and their branch-local code
├── design-system/    # domain-independent public UI (App* components)
│   ├── ui/           # private shadcn and vendor-like primitives
│   └── index.ts      # curated public exports
├── components/       # components reused by several page branches
├── layouts/          # persistent and route-level layouts
├── {{HOOKS_DIR}}/    # globally reusable reactive behaviour
├── utils/            # globally reusable pure functions
├── model/            # globally reusable frontend model classes
├── payload/types.ts  # globally shared backend transport contracts
├── types.ts          # globally shared frontend-only types
├── actions/ routes/ wayfinder/   # generated by Wayfinder, never edited
```

- Code MUST start in the page branch that owns it. Its components, {{HOOKS_DIR}}, utils, models,
  payload contracts and types live directly below that branch.
- Per-page directories such as `Index/components` MUST NOT be introduced; a branch-level
  `components` directory is used even with one consumer.
- Code moves to a global location only when it has consumers in **separate page branches**, and
  only as far outward as needed. Moving code outward "because it might be reused" is prohibited;
  brief duplication is fine until real consumers show the shared boundary.
- Reuse alone does not make a component part of the design system (see below).
- No `components/shared` and no generic `lib` directory. `utils` holds stateless functions only;
  reactive or lifecycle-aware behaviour is a {{HOOK_NAMING}}.
- Global modules MUST NOT import from `pages`. Imports outside the current branch use `@/`.
- Hand-maintained directories use kebab-case. Renaming an Inertia page path updates the
  `Inertia::render()` name in the same change.

```text
pages/catalog/products/components/ProductSummary   one page branch
          │ reused by another branch
          ▼
components/ProductSummary                          several branches
```

### Structure checks

The rules above are checked, not only reviewed:

- `pnpm frontend:structure` — directory names, locality and import direction;
- `pnpm frontend:inertia-page-paths` — every `Inertia::render()` name has a page with the same
  path and casing;
- `pnpm frontend:check` — every frontend check in sequence with a summary ([tools.md](tools.md)).

## Components

- Pages compose route-level screens and coordinate Inertia data. Pages and application components
  compose the public design-system components; they do not reimplement generic controls.
- Every component has one clear responsibility. Prefer composition, props, events and slots over
  hidden global state.
- Props and events are typed and props are never mutated. Derived state is computed; effects
  are reserved for real side effects and clean up timers, listeners and requests.
- List keys are stable domain ids, never array indexes when items can change order.
- Extract before extending a component that approaches 500 lines or mixes UI, business and
  transport logic.
- Component files use PascalCase; application components have multi-word names.

<!-- optional: Vue -->
### Vue

- Single-file components with `<script setup lang="ts">`, then `<template>`, then optional
  `<style scoped>`.
- Script order: package imports; `@/` imports; branch-local imports; named type aliases; contract
  macros (`defineModel`, `defineProps`, `defineEmits`, `defineSlots`, `defineExpose`);
  composables; hydrated models; local state; computed values; handlers; watchers and lifecycle.
- Contracts are named `type` aliases (`Props`, `Emits`, `Slots`), never inline object types in a
  macro. `Emits` uses call signatures: `(e: 'select-item', item: Item): void`.
- `defineProps()` is never destructured, and templates access props by name, never via `props.`
  or `$props`.
- Template tags, attributes and custom events use kebab-case (`<app-button>`,
  `@select-item`). Composables are named `useXxx.ts`.

<!-- optional: React -->
### React

- Function components in `.tsx`. Module order: package imports; `@/` imports; branch-local
  imports; named type aliases; the component; hooks; hydrated models; local state; derived
  values; handlers; effects.
- Contracts are named `type` aliases (`Props`), never inline object types in a signature. Props
  MAY be destructured, but not renamed to work around a collision.
- Callback props are named `onXxx`, their handlers `handleXxx`. Hooks are named `useXxx.ts`.
- An effect is not used to derive state; it synchronises with something outside React.

## Design system

- `resources/js/design-system` is the domain-independent public UI module. Pages, layouts and
  application components consume it only through the curated entry point `@/design-system`.
- **Public design-system components use the `App` prefix** (`AppButton`, `AppTable`). Private
  primitives in `design-system/ui` are imported only inside the design system, with the `Ui`
  prefix (`Button as UiButton`). Application code MUST NOT import a `Ui` primitive.
- An unchanged primitive MAY be exported with an `App` alias
  (`export { Button as AppButton } from './ui/button'`). A dedicated `App` component is created
  only when it narrows the API, sets application-wide variants or composes primitives; a
  component that forwards everything is not created.
- The design system MUST NOT import pages, application components, models, payload contracts,
  Wayfinder or Inertia, and contains no domain names, rules, routes or copy.
- Private primitives change only for upstream sync, accessibility, security, correctness or a
  deliberate design-system-wide change. A generator such as the shadcn CLI writes into
  `@/design-system/ui` and uses `@/utils/classes` for `cn()`.
- A new visual pattern starts in its page branch and is promoted once its domain-independent
  contract is clear and real reuse justifies it.
- Inertia components that collide with native elements are aliased: `Link as InertiaLink`,
  `Head as InertiaHead`, `Form as InertiaForm`.

### Accessibility

- The design system owns keyboard interaction, focus management, visible focus, ARIA relations
  and the disabled, loading, invalid, empty, success and failure states of reusable controls.
  Application code never rebuilds them.
- The consuming page provides labels, descriptions, errors, headings and alternative content.
- Colour is never the only carrier of a state. Buttons are for actions, links for navigation.
- Asynchronous success or failure is announced through the design system's feedback component.

## Tailwind CSS

- Tailwind 4, configured CSS-first in `resources/css/app.css`; no JavaScript Tailwind
  configuration and no deprecated v3 utilities.
- Utility classes live primarily in design-system components. Outside them, utilities are for
  route-level layout and genuinely local presentation; repeated class groups are a signal of a
  missing component, variant or token.
- Consumers never override a design-system component's internals with classes; add a variant.
- Colours, type, spacing and radii come from the semantic tokens in `app.css`, which mirror the
  Pencil design. No hex values and no arbitrary values where a token exists.
- Use `cn()` from `@/utils/classes` for conditional classes. Prefer `gap` over sibling margins.
- Icons are imported by name as components and never resolved from strings. Decorative icons are
  hidden from assistive technology; icon-only controls have an accessible name.

## TypeScript, payloads and models

- Page props, component contracts, form data and payloads are modelled explicitly. `any`, unsafe
  casts and non-null assertions SHOULD NOT be used; external values are narrowed at the boundary.
- Backend transport contracts live in the nearest `payload/types.ts`, keep backend field names
  and carry the `Payload` suffix (`ProductPayload`). Frontend-only types live in `types.ts`.
- Payload types stop at the owning page. Child components take frontend models or narrow props
  and never read page props globally for data that can be passed.
- A frontend model is created explicitly from a payload (`fromPayload()`) and converts back
  explicitly (`toPayload()`). Class instances never cross the Inertia boundary.
- Server-owned enums and lookup values are not duplicated; the backend passes them.
- Type-only imports use `import type`; switches over unions end with an exhaustive `never` check.

## Inertia data flow

- Server props are the source of truth. They are copied into local state only for a deliberate
  local draft.
- Props are minimal and serializable and carry only what the acting user may see. Filtering in
  the browser is not authorization.
- Internal navigation uses `InertiaLink` or `router`, never `window.location` or a plain `<a>`.
- Numbers, amounts and dates arrive formatted from the server; the frontend never formats, parses
  or recomputes them ([domain.md](domain.md#money)).
- Deferred props render a purposeful fallback; partial reloads, polling, prefetching and
  optimistic updates are used only when their stale-data and rollback behaviour is handled.
- Every request has visible processing, empty, success and failure states, and duplicate
  submission is prevented.

## Routes and forms

- Every Laravel route the frontend calls goes through generated Wayfinder functions, imported by
  name from `@/actions` or `@/routes`. URLs are never hardcoded and generated files never edited.
- Ordinary forms use Inertia's form component; `useForm` when the form needs programmatic
  control. Every control has an accessible label and a stable `name`; server errors attach to
  their control; entered values survive a validation error.
- Client validation MAY improve usability; it never replaces form request validation.

## Performance

- Large datasets use server-side filtering and pagination; whole collections are never fetched to
  filter in the browser.
- Remote search is debounced and stale requests are cancelled or ignored.

## Frontend tests

- Vitest covers pure functions, model transformations, non-trivial {{HOOKS_DIR}} and concrete
  regressions. Prefer extracting logic into a function over mounting a component to reach it.
- Component tests are added only for user-observable behaviour that cannot be tested more
  directly. No snapshots as a substitute for assertions, no tests of markup, styling, prop
  forwarding or framework behaviour.
- Authorization, validation and payload shape are tested in Laravel feature tests; Vitest never
  duplicates them.
